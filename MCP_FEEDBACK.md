# Runtime feedback через MCP

Владелец контракта и загрузки находится в `@tradejs/node/diagnostics`.
Владелец очереди host executor находится в TradeJS-Deploy. Торговые команды и
конфигурация стратегий в этот процесс не входят.

## Контракт подключения

`tradejs_info.feedbackContract` объявляет версию и обязательные инструменты.
Клиент передаёт фактический ответ своего `tools/list` в
`assertMcpFeedbackContract`. Наличие методов в исходниках или в ответе info
не подтверждает, что подключение клиента обновило их схемы.

`worker.replayAvailable` означает наличие совместимого host runner.
`worker.replayReadiness` отдельно показывает готовность по памяти. Признак
`ready` не резервирует память: окончательная проверка выполняется host runner
под общей блокировкой. Новый worker требует host protocol version 2.

## Загрузка и обработка

`downloadMcpBundle` получает каталог файлов из `diagnostics_get_report`, версию
контракта, фактические схемы инструментов и callback `readChunk`. Callback
использует существующее авторизованное подключение и возвращает распакованный
`structuredContent.data` ответа `artifact_get`. Модуль не читает токены, не
открывает OAuth и не делает прямые HTTP-запросы.

Транспортный адаптер переводит временные ошибки чтения в
`McpReadTransportError`, сохраняя `retryAfterMs`. Ошибки прав, checksum,
протокола и внешней формы данных повторять нельзя. Запуски jobs этот модуль
не повторяет и вообще не вызывает.

Состояние хранится в `<root>/<opaque artifact id>/`: частичные bytes и descriptor
позволяют продолжить с точного offset. Полные исходные файлы проверяются по
своим размерам/SHA-256 и общему verifier. Последним публикуется скачанный
`.complete`, без изготовления новых исходных markers. Параллельный импорт
одного каталога блокируется. После аварийного завершения самого процесса
может остаться `.download-lock`: перед его удалением оператор должен
подтвердить отсутствие другого загрузчика. Автоматического снятия такого
блокирования пока нет.

После загрузки двух потоков запустите из Project:

```bash
yarn exec tradejs runtime-feedback-process \
  --runtimeDir <complete-runtime-bundle> \
  --replayDir <complete-replay-bundle>
```

Команда не запускает replay и не загружает свечи. Она проверяет точную пару,
читает verified историю из `data/runtime-evidence/artifacts/production`,
пишет calibration, все embedded enabled per-strategy scorecards и aggregate
в уникальный каталог `output/runtime-feedback`, затем schema-v2 receipt.
Paused enabled стратегии также обрабатываются. Повторная точная пара
возвращает существующий receipt. Несовместимый receipt блокирует обработку.
Один receipt не доказывает полноту multi-composition периода: вызывающая
автоматизация должна сопоставить все обнаруженные составы окна.

## Подготовка релиза

1. Выпустить согласованный набор Framework и Deploy после локальных checks.
   Проверить полный диапазон накопившихся коммитов перед публикацией.
2. Установить host runner protocol v2 и новую cron-схему из Deploy до запуска
   нового worker. Cron публикует запросы через `--enqueue-daily`; минутный
   runner обслуживает ту же очередь, что MCP. Старые failed результаты
   сохраняются и автоматически не перезапускаются.
3. Опубликовать точную Framework cohort, обновить Project dependency штатным
   процессом, выполнить Project checks/image smoke и согласованный Deploy
   handoff. Не менять gate, risk или production strategy config.
4. Проверить actual client tools/list и contract assertion. Если требуется
   обновить подключение или consent, это делает пользователь.
5. До полноценного replay обеспечить измеренную ёмкость памяти. Изменения
   очереди лишь позволяют ждать ресурсы и не увеличивают RAM.
6. Отдельно разрешить контрольный replay новой точной пары. Проверить полный
   download и receipt каждого состава. Старые failed jobs не повторять.
7. Подтвердить три последовательных полных суточных окна без ручного SSH.

## Локальные проверки и их пределы

HTTP contract tests используют MCP SDK и настоящий API handler. Тест загрузки
использует настоящий artifact catalog/storage/verifier с подменой только
доступа к авторизованному пользователю. Интеграционный тест двух потоков
проходит publisher/sealer, downloader, calibration, scorecards и receipt.
Replay evidence в нём является fixture: он не исполняет production image.
Тесты Deploy выполняют настоящий broker с тестовым shell executor, включая
ожидание ресурсов, повторную пару и сохранение исторического failed result.

Реальное OAuth-подключение, Docker image replay, состояние production и
доступная host RAM этими локальными тестами не подтверждаются.

## Профиль памяти replay

Для отдельно разрешённого диагностического процесса можно задать
`TRADEJS_REPLAY_MEMORY_PROFILE` абсолютным путём к writable JSONL-файлу.
Профиль содержит PID, этап, счётчики, RSS, heap и максимальный RSS процесса.
Он не содержит свечи, торговые ключи или исходные payload и не вызывает GC.
Подготовка истории/стратегий, исполнение, освобождение runtime-замыканий,
сборка результата и запись JSON имеют отдельные отметки. Несколько child
processes различаются по PID; их пики нельзя складывать без учёта перекрытия.

После исполнения временный план освобождается перед сборкой отчёта. История
во время исполнения, время и порядок инструментов не меняются. JSON sidecar
и replay evidence записываются частями через временный файл и atomic rename.
Новая запись компактная; значения полей сохраняются, но whitespace и SHA-256
нового файла отличаются от старой pretty-записи. Старые sealed bundles не
переписываются. Writer предназначен для plain JSON evidence и явно отклоняет
циклы и custom toJSON hooks, чтобы не менять данные молча.

Измерения синтетического стенда не являются основанием снижать production
memory limit. Для этого нужен полный разрешённый прогон реального immutable
входа с production-стратегиями и запасом памяти.
