# Автоматическое исследование стратегии

Вызов: `$strategy-research`. Название стратегии возьми из текущего чата.
Можно указать его явно: `$strategy-research TrendLine`.

Результат поручения — выполненное исследование, проверенный отчёт и короткий
вывод. Создание спецификации само по себе не завершает задачу.

## Восстановить контекст и выбрать запуск

1. Прочитай применимые `AGENTS.md`. Установи одну точную стратегию, её репозиторий,
   конфигурацию и последние записи в Project `notes/<Strategy>/`,
   `data/research/strategy/`, `data/research/core/` и журнале кандидатов.
   Используй контекст текущего чата, не обследуй все стратегии.
   Сохрани причины прежних отказов и происхождение выбранной конфигурации.
   Не называй локальную конфигурацию фактическим состоянием production без
   привязанных runtime evidence.
2. Сначала найди подходящий незавершённый `research:strategy` запуск. Если его
   условия, исходники и исполняемые модули не менялись, возобнови тот же `run`.
   Не пересобирай инструменты и не создавай заменяющий researchId до проверки
   возможности возобновления. Несовпадение lineage — причина отдельного
   исследования, а не разрешение переписать старую запись.
3. Для завершённого запуска на действительно новом покрытом периоде используй
   `revalidate`, если вопрос касается прежнего замороженного правила.
   Период должен начинаться не раньше конца родительского исследования.
   При новой гипотезе или изменённых параметрах создай новый researchId через
   `init`. Не переиспользуй родительские исходы для нового подбора.
4. Если стратегию нельзя однозначно установить из чата, задай один короткий
   вопрос с найденными вариантами. Иные решения восстанови из доступных
   записей; спрашивай только о существенной неустранимой неоднозначности.

## Зафиксировать условия

Для нового исследования выбери воспроизводимую исходную конфигурацию и
небольшой набор обоснованных вариантов параметров. Для каждого запиши причинную
гипотезу и ожидаемое изменение поведения. Учти уже отвергнутые варианты.
Если готовых альтернатив нет, достаточно одного исходного ядра: команда сама
исследует его фильтр. Не придумывай альтернативы ради заполнения бюджета.

Зафиксируй до расчётов общий период, список USDT-контрактов, расходы, риск,
критерии отбора и ограничения ресурсов. Используй сохранённую историю с
`--cacheOnly`. Выбери сопоставимое покрытое окно по предыдущим исследованиям
и доступным свечам. Не сокращай период или набор инструментов молча и не
обновляй историю без отдельного запроса.

При отсутствии явно заданных значений сохрани бюджеты и критерии,
сформированные `init`. До первого запуска укажи пользователю выбранные условия
кратким сообщением и продолжи работу без запроса рутинного подтверждения.
Бюджет — предел работы, а не требование потратить его целиком.

`testSince: 0` определяет внешнюю границу 60/40 по группам времени исходного
ядра. Для сопоставления с прежними выгрузками сохрани их общую календарную
границу. Ранее открытые данные всегда помечай `history: retrospective` и
перечисляй связанные `priorResearchIds`. Новый календарный период сам по себе
не доказывает, что его исходы ещё не изучались. При необходимости исправь
созданную `revalidate` спецификацию до её первого `run`.

## Выполнить существующую команду

Перед командами выбери Node.js 24 по `.nvmrc` и проверь `node --version`.
Не используй Node 20 из оболочки по умолчанию. Все рабочие команды выполняй
из `tradejs-project`. `PROJECT_CWD` указывает на
него, `TRADEJS_SOURCE_REPOSITORY_ROOT` — на точный checkout стратегии,
`TRADEJS_FRAMEWORK_REPOSITORY_ROOT` — на framework checkout, чьи модули выполняют
исследование. Не смешивай исходники, build и установленные версии.

Используй установленный `yarn exec tradejs research:strategy`, если выбранный
CLI и его Node runtime поддерживают этот процесс. В каноническом workspace
можно явно выбрать собранный framework CLI:

```bash
node "$TRADEJS_FRAMEWORK_REPOSITORY_ROOT/packages/cli/dist/cli.js" research:strategy --help
```

Если для нового запуска нужна сборка, выполни её в выбранном framework
checkout до фиксации исполняемой lineage. Не публикуй пакеты и не меняй
зависимости Project ради запуска. После выбора CLI используй его для всех
этапов, включая дочерние команды. Не подменяй отказ preflight другим runtime.

Примеры аргументов после `research:strategy`:

```text
init --coreSpec data/research/specs/<core>.json --out data/research/specs/<workflow>.json
init --strategy <Strategy> --config <Strategy:config> --researchId <id> --claim <гипотеза> --mechanism <механизм> --symbolsFile <USDT.json> --start <UTC> --end <UTC> --out data/research/specs/<workflow>.json
run --spec data/research/specs/<workflow>.json
status --spec data/research/specs/<workflow>.json
verify --spec data/research/specs/<workflow>.json
revalidate --spec <parent-workflow.json> --researchId <new-id> --start <UTC> --end <UTC> --out data/research/specs/<new-workflow>.json
```

Для `init` по именованным конфигурациям можно добавить
`--candidates <Strategy:a,Strategy:b>`. Каждая такая конфигурация должна
описывать одну ячейку сетки. Для иной подготовленной доски вариантов используй
фиксированную `research:core` спецификацию через `--coreSpec`.
Не меняй рабочую конфигурацию стратегии или чужие Redis-сетки.

Перед запуском проверь активные tester workers и память. Выполни `run` и
дождись результата. Команда владеет бэктестами, поиском правил на DEV,
замораживанием кандидата, TEST, подтверждением, отчётом и очисткой.
Не запускай рядом второй исследовательский процесс и не заменяй команду
ручным набором несопоставимых бэктестов.

После технического сбоя устрани доступную причину и повтори тот же `run`
только при сохранённой lineage. Не увеличивай бюджет задним числом и не
создавай дубликат активной задачи. Если препятствие требует новых данных,
авторизации или изменения условий, сохрани точную причину и доступный отчёт.
Интерактивную авторизацию выполняет пользователь.

## Проверить результат и завершить

Выполни `verify` и `status`. Проверь наличие и читаемость
`data/research/strategy/<researchId>/report.html`, итогового `result.json`,
постоянной записи исследования и состояния очистки.

В отчёте проверь сравнение каждого ядра со старым и найденным фильтром,
ALL/LONG/SHORT, расходы, задержку входа, концентрацию и ограничение общего
риска. Диагностика должна показывать покрытие BaseContext, распределения
индикаторов и доступные примеры сделок. До раскрытия исхода график должен
показывать только данные, доступные при решении. Отсутствующие свечи или оценки
Jev укажи как пробел, не заменяй их догадкой. Используй только сохранённые или
локальные оценки Jev; платные запросы не входят в этот вызов.

Направления выбираются по уже рассчитанным сделкам DEV. Команда сохраняет
решение и его причины до открытия TEST: оба направления, только LONG, только
SHORT либо ни одного при недостаточном результате. Прибыльное направление
исходной конфигурации остаётся отдельным вариантом контроля на DEV.
Три отдельных бэктеста на каждую гипотезу не нужны. Разбивка сделок служит
предварительной диагностикой; штатный тестер подтверждает фактические входы
выбранного кандидата вместе с неизменным исходным контролем.
При включённом Jev добавляется второй вариант замороженной пары сравнения.
На новом периоде сохраняются прежние направления, новые исходы не меняют выбор.

При настроенном `JEV` сравнение с Jev и без него выполняется автоматически.
На DEV команда отдельно подбирает фильтры с оценками Jev и без них в пределах
общего бюджета поиска. Вариант без Jev не содержит настройки `JEV` и правил,
зависящих от его оценок. На TEST проверяется одна заранее выбранная пара на
одинаковом ядре, рынке, периоде, расходах и общей маске направлений. Пара,
предпочтение DEV и правила входят в замороженный выбор; на новом периоде они
не пересматриваются. Не запускай отдельные тесты трёх направлений ради Jev.

Проверь раздел «Что добавляет Jev» в HTML и `jevComparison` в результате:
разницу PnL, просадки, ALL/LONG/SHORT, покрытие оценками и интервал средней
дневной разницы PnL. Нулевые оценки или недостаточную поддержку нельзя
выдавать за пользу. Ретроспективный эффект остаётся ретроспективным, а провал
выбранного кандидата на TEST не разрешает заменить его вторым вариантом.
При отсутствии настройки Jev сравнение помечается как невыполненное; модель,
история оценок и платные запросы автоматически не создаются. Торговый PnL
не включает историческую стоимость получения оценок Jev. Сохранённая копия
локальной модели и её контрольная сумма входят в постоянные записи.
Обучение и валидация локальной модели должны закончиться до границы TEST;
команда останавливается при пересечении этой границы или отсутствии дат.

Не меняй правила после открытия TEST и не заменяй проигравшего кандидата
другим. Ретроспективный успех не является независимым подтверждением.
Срабатывание общего лимита риска требует совместной проверки исполнения,
которую нельзя заменить фильтрацией старых сделок.

Очистку выполняет штатный механизм после проверки постоянных записей.
При `retention-status.json: pending` прочитай причину. Если файлы ещё
используются, сохрани их и повтори тот же `run`, когда потребитель завершится.
Не удаляй их вручную. Новые вопросы на уровне отдельных сделок после очистки
требуют нового воспроизводимого прогона замороженного кандидата.

Заверши кратким ответом по-русски: что проверено, какой вариант выбран или
почему отклонён, выбранные направления с причинами, основные ALL/LONG/SHORT результаты после расходов, ограничения
доказательств и следующий шаг. Дай абсолютные ссылки на HTML-отчёт,
спецификацию и постоянную запись; укажи проверку контрольных сумм и очистку.
Всегда передавай итоговый HTML-отчёт со встроенными графиками доходности и
просадки TEST, результатами направлений и примерами сделок. Проверь, что
отчёт открывается самостоятельно и на узком экране; внешняя сеть для графиков
не требуется. Не выдавай промежуточную разбивку DEV за результат отдельных
нативных бэктестов направлений.
Не обещай будущую прибыль. Публикация, уведомления, deployment и реальные
сделки не входят в этот навык.

Если пользователь отдельно просит менять детектор или вести несколько раундов
изменения исходников, используй
[`strategy-improvement-research`](../strategy-improvement-research/SKILL.md)
в пределах этого запроса. Сам по себе `$strategy-research` таких изменений
не требует и не запускает соседний процесс улучшения.
