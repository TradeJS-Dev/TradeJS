# Варианты и совместное состояние в TradeJS

Сначала посмотри существующий контракт, например
`apps/app/src/app/components/Shared/Filters/Root/index.tsx`:
владелец передаёт `filters`, данные и действия через `FiltersContext.Provider`.
Это пример сохранения одного владельца, а не требование вводить контекст
для каждого фильтра.

Когда режимы взаимоисключающие, один `variant` или discriminated union может
исключить невозможную комбинацию лучше нескольких boolean. Независимый
`disabled` оставь независимым. Если различаются содержимое и расположение,
общая рамка с `children` проще общего компонента с множеством новых флагов.
Составные части оправданы, когда используются самостоятельно.

Для совместного состояния сначала подними существующего владельца к общему
предку. Контекст вводи при реальной необходимости передачи через дерево;
хук чтения держи рядом с контекстом. Проверь два независимых экземпляра,
обновление от владельца и сохранение состояния при переходах по задаче.

У Chakra UI уже есть составные primitives. Пример адаптера проекта —
`apps/app/src/app/components/UI/Select/index.tsx`: использует
`Select.Root`, `HiddenSelect`, trigger и portal. Не обходи их клавиатурный
контракт новой самодельной реализацией. Сохраняй controlled/uncontrolled,
callbacks, ref, portal и фокус, если они входят в контракт потребителя.

Граница `'use client'` определяется интерактивностью, а не желанием
унифицировать компоненты. Не тяни Node/infra-модули в клиентское дерево.
Сверяй текущую границу и поддержку API, прежде чем менять архитектуру Next.js.

При рефакторинге общего компонента проверь реальные потребители, а не только
новый helper; не перестраивай все экраны ради одного варианта.
