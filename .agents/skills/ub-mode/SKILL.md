# Минимальное полное решение

Применяй при реализации, исправлении и рефакторинге. Сначала прочитай
[границы TradeJS](../task-planning/references/tradejs-context.md), затем
[Ponytail](references/ponytail.md): существующий владелец и средства проекта,
платформа, установленная зависимость, необходимый новый код.

- Установи причину проблемы и нужных потребителей до выбора правки. Не
  компенсируй неверный переход дополнительной синхронизацией состояния.
  После повторных неудачных попыток пересмотри гипотезу и воспроизведение.
- Сначала определи допустимые данные, состояния и владельцев. Чистая логика
  не зависит от UI, сети и хранения. Не смешивай browser-safe `core`, Node
  runtime и `infra`; стратегия не размещает ордера напрямую.
- Сохраняй строгие типы: переиспользуй контракт владельца, проверяй внешние
  неизвестные данные на входе, не скрывай ошибку типов `any` или двойным `as`.
  TypeScript не подтверждает форму ответа API во время работы.
- Держи один источник изменяемого состояния там, где оно действительно общее;
  разным экземплярам не навязывай глобальный singleton. Для повторяемой
  операции сохрани требуемую идемпотентность и жизненный цикл ресурса.
- Новая функция, хук, класс или адаптер должны иметь самостоятельную
  обязанность. Маленький diff и минимум строк не оправдывают неправильную
  границу. Не вводи настройки и совместимость на вырост.
- Работай небольшими проверяемыми частями. Перед изменением сложного поведения
  найди существующую защиту; при необходимости добавь тест результата, а для
  воспроизводимого дефекта сначала подтверди исходное падение, когда практично.
  Не требуй нового теста для каждой обратимой малорисковой правки.
- Автоматизируй повторяемую работу после понятного примера. Не вводи новые
  инструменты метрик, CRAP-пороги или mutation testing ради наличия чисел.
  Используй существующие проверки и пороги, соответствующие риску.

Для нового механизма читай
[выбор решения](../task-planning/references/implementation-decisions.md),
при самопроверке — [правила ревью](../task-planning/references/review-standards.md).
Тесты выбирай по [качеству покрытия](../task-unit-test-coverage/references/test-quality.md).
После изменения кода выполняй применимые команды репозитория. Не повторяй
успешную полную проверку без новых изменений или причины.

Кратко сообщи, что изменено, почему, как проверено и какое существенное
ограничение осталось. Навык не добавляет обязательных согласований или
субагентов и не разрешает commit, push, публикацию, сообщения, удаление данных
или внешние операции сверх текущего поручения.

Адаптация принципов Robert C. Martin через DevHub;
[авторство и ограничения лицензии](../task-planning/references/sources.md).
