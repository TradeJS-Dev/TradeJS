# Браузерная проверка TradeJS

Выбирай этот уровень для поведения браузера, геометрии или реального пути
через приложение. Для обычного условия/расчёта достаточно нижнего уровня по
[качеству тестов](test-quality.md). Здесь не требуется отдельный сервис
регистрации, мониторинг или новый формат отчёта.

## Среда и границы запуска

В `playwright.config.ts` задан `testDir: './e2e'`, Chromium,
`QUICKSTART_E2E_URL` и trace при падении. `webServer` отсутствует. Из
`investing/` адресный запуск сохранённого файла выглядит так:

```sh
yarn exec playwright test e2e/quickstart.spec.ts --project=chromium
```

Этот пример требует отдельного чистого тестового приложения: существующий
`quickstart.spec.ts` создаёт локального пользователя и запускает backtest.
Не направляй его на личный или production runtime. Подготовку, точный URL,
сборку и доступность зависимостей установи до запуска. Новый адресный сценарий
запускай с его фактическим путём, не выдавай quickstart за покрытие всех экранов.

`yarn quickstart:e2e` в `investing` — полный установочный сценарий через
`bin/quickstart-e2e.sh`: создаёт отдельный Project, запускает инфраструктуру и
приложение, затем удаляет созданное дерево и его тома. Используй только для
задачи, где такая подготовка и очистка разрешены, после проверки конкретного
пути и скрипта. Не выбирай эту команду как бесплатную проверку любого UI.
Она по умолчанию использует опубликованный `create-tradejs`, поэтому свяжи
версию пакета с проверяемым исходным изменением до вывода об исправлении.

`yarn sandbox:e2e` выполняет CLI/расчётные проверки опубликованных пакетов и
не является браузерным прогоном. Публикующий CI тоже не запускается ради
проверки интерфейса.

Интерактивная авторизация пользователя, OAuth, device-code, повторный вход и
повышение прав остаются действиями пользователя по `AGENTS.md`. Недоступный
доступ обозначь конкретным блокером, продолжая независимые проверки. Навык
не разрешает торговые операции, создание production jobs, удаление данных,
уведомления или изменение внешних систем. Не печатай cookies, токены и `.env`.

## Сценарий и доказательство

- Используй настоящий изменённый UI, стили, шрифты и нужные providers.
  Копия DOM или jsdom не доказывает геометрию. Мок API допустим на границе;
  результатом с ним не подтверждай настоящую серверную интеграцию.
- Найди существующие сценарии. В TradeJS нет обязательного общего Page Object
  registry: импорт `test`/`expect` из `@playwright/test` принят в текущем e2e.
  Выделяй повторяемые локаторы/действия по мере необходимости, не создавай
  framework тестов ради одной страницы. Моки, действия экрана и ожидания
  сценария имеют разные обязанности.
- Один тест проверяет связный исход и не зависит от соседей. Смысловые этапы
  длинного сценария отмечай `test.step`; не создавай шаг на каждый клик.
  Небольшая параметризация допустима, если каждый случай виден отдельно и
  не меняет последовательность действий скрытыми флагами.
- Выбирай устойчивые локаторы по роли и доступному имени в нужной области.
  Не используй глобальное `.first()` для обхода неоднозначности. Ожидай
  наблюдаемый результат штатными assertions, а не фиксированную задержку.
- Для геометрии проверь реальные границы, clipping родителя, перенос, фокус
  и доступность действий. Отсутствие горизонтального скролла не доказывает,
  что текст и кнопки видимы. Учитывай узкий экран и длинные данные по риску.
- Фиксируй сценарий, проверенную сборку/SHA и грязные изменения, URL,
  существенные моки, ожидаемое и фактическое состояние, exit status и итог.
  При неизвестной версии ограничь вывод. Снимок и trace прикладывай только
  если получены; они могут содержать чувствительные данные.

Если обязательный браузерный путь недоступен, выполни доступные полезные
проверки и назови точный оставшийся пробел. Не объявляй unit запасным e2e,
не добавляй пустую/skip spec ради формального покрытия. Закрывай только свои
тестовые сессии и процессы, не чужие вкладки и работающие сервисы.
