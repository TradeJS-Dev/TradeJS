# Качество тестов

Сначала найди существующее покрытие поведения и потребителей. Сохрани в
обычном плане связь «риск → существующая проверка → недостающий результат →
место дополнения». Если покрытие достаточно, новый тест не нужен.

Разделяй разовую приёмку и постоянную защиту. Для локальной малорисковой
визуальной правки бывает достаточно воспроизводимых шагов и наблюдения на
известной версии. Для расчётов, прав, потери данных и взаимодействия модулей
выбирай покрытие по риску, а не размеру diff.

| Что может сломаться | Минимальный достаточный уровень |
| --- | --- |
| Условие, расчёт, преобразование | Unit через контракт владельца |
| Компонент, store, адаптер, порядок взаимодействия | Компонентная или интеграционная проверка реальных участников |
| Размер, перенос, clipping, шрифты, фокус в браузере | Реальный компонент со стилями в браузере |
| Маршруты и связность подсистем | E2E через приложение, если нижний уровень не обнаружит разрыв |

Не требуется сначала неуспешно пытаться e2e. Для нового e2e назови поломку,
которую более низкий уровень пропустит. Полную матрицу условий проверяй внизу,
на уровне приложения оставляй представительные проверки связности.

## Содержательный сценарий

- Ожидание следует из задачи, а не скопировано из реализации. Изменение
  внутренней функции, порядка чистых вычислений или разметки без изменения
  контракта не должно ломать тест.
- Проверяй настоящий код. Мокируй сеть, IO, время или другую внешнюю границу,
  но не результат проверяемой логики. Успех с mock backend не доказывает backend.
  Интеграционный тест не заменяет обоих взаимодействующих участников моками.
- У каждого сценария свои предусловия. Контролируй время, данные и ответы;
  восстанавливай подмены. Для двух экземпляров проверяй независимость там,
  где она требуется. Не меняй общие данные параллельно.
- Имя сообщает условие и исход. Небольшая таблица подходит для одинаковых
  действий с разными данными. Разные последовательности действий — отдельные
  сценарии; универсальный runner не должен прятать смысл.
- Assertions различают правильное поведение и исходную поломку. Видимость
  кнопки не доказывает сохранение данных, один вызов helper — весь путь.
  Точный текст, стиль или кратность вызова проверяются, когда входят в контракт.
- Асинхронное ожидание привязано к результату или событию. Произвольная пауза
  и повышенные retries не исправляют гонку. Проверь поздние success/error/finally
  старого запроса, если меняется актуальность состояния.

Оцени весь добавленный объём: fixtures, helpers, providers, настройки и моки.
Если проверка простого поведения требует новой инфраструктуры, пересмотри
границу. Не дублируй сценарий ради одного assertion; дополни существующий,
если его предусловия подходят. Новая spec нужна для отдельного поведения или
несовместимых fixtures, а не для каждого критерия.

## Доказательства и достаточность

Для дефекта по возможности покажи исходный сбой на сопоставимой базе. Ошибка
setup не подтверждает регрессию. Snapshots принимай после разбора изменений;
не скрывай проверяемое состояние маской. Запуск на другой сборке, `--list`,
skipped или статический анализ не являются исполнением сохранённого теста.

Достаточный успешный unit/integration закрывает свой критерий. Возражение
должно называть конкретную пропущенную поломку. Отсутствие e2e само по себе
не блокер. Непроверенная геометрия, обязательный путь или неизвестная версия
остаются ограничениями, если именно они нужны для вывода.

При падении установи причину: продукт, тест, окружение или упаковка. Не
ослабляй assertions и не заменяй обязательный тест ручным pass. После
исправления повтори затронутые проверки и учитывай существующие релевантные
регрессии общего модуля. Не переписывай всё старое покрытие по этому документу.
