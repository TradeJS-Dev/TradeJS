# Покрытие поведения задачи

Применяй по запросу тестов или когда изменённое поведение требует защиты от
конкретной регрессии. Начни с [качества тестов](references/test-quality.md) и
[команд проекта](../task-planning/references/tradejs-context.md).

1. Найди репозиторий и пакет-владелец, изменённый контракт, потребителей и
   ближайшие тесты. Прочитай условия, моки и assertions: совпадения имени мало.
2. Выбери: уже достаточно покрытия; достаточно разовой проверки; нужен новый
   постоянный тест. Для нового теста назови дополнительную поломку, которую
   он обнаружит. Не добавляй тесты ради числа строк, процента или ритуала.
3. Выведи ожидаемый результат из требований. Выбери применимые позитивный,
   негативный и регрессионный случаи. Используй минимальный достаточный
   уровень. UI-задача не означает автоматическую необходимость e2e.
4. Используй существующие настройки Jest/Testing Library, соседний `__tests__`
   и TypeScript. Проверяемый код оставь настоящим; моки ставь на внешней
   границе. Не добавляй новый setup ради обхода окружения. Не переноси чужие
   `any` и массовые моки как стандарт новых тестов.
5. Для бага, когда практично, получи падение из-за исходного дефекта до
   исправления. Не меняй чужое дерево; недоступную базу укажи ограничением.
   Не восстанавливай старый баг внутри каждого постоянного теста.
6. Выполни адресные тесты и применимые проверки типов/линтера. В `investing`
   после правок кода сначала требуется `yarn prettify`; перед широкой
   проверкой учти, что эта команда форматирует и соседние файлы. Для изменения
   общего экспорта проверь сборку потребителей: Jest aliases этого не заменяют.
7. Дождись завершения и exit status. Повторяй проверки после изменения входов,
   кода или обнаружения новой причины, а не потому, что начался новый этап.

Для асинхронной логики проверяй актуальность результата после смены входов,
значимый порядок и кратность эффектов, очистку ресурса, если это часть риска.
Для Node-кода сверяй окружение соседних тестов; root Jest по умолчанию jsdom.
Snapshots обновляй только после просмотра намеренных отличий, без массового
принятия. Не снижай assertions или coverage thresholds ради зелёного статуса.

Для геометрии или пути через приложение читай
[браузерное покрытие](references/browser-coverage.md). Разовая визуальная
проверка не обязана становиться постоянной spec. При явном запросе e2e
выполняй браузерный уровень либо объясни конкретный блокер.

Верни критерий, сценарий, уровень и фактический результат: команда и cwd,
проверенная версия, существенные моки и ограничения. `--list`, skipped,
ручной просмотр и написанный тест не являются прошедшим тестом. Достаточный
успешный unit/integration закрывает свой критерий без формального требования
e2e. Навык не разрешает внешние записи, публикацию, удаление данных или вход
в аккаунты сверх полномочий задачи.
