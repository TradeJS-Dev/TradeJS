# Планирование задачи

Начни с [карты workspace и проверок](references/tradejs-context.md). Выбери
репозиторий по корневому `AGENTS.md`, затем прочитай его инструкции и правила
затронутого пакета. Не обследуй все соседние репозитории. Состояние рабочего
дерева и существующие изменения учитывай до правок.

## Установить факты

1. Сформулируй ожидаемый результат и границы поручения. Отдели требования от
   наблюдений и предположений о реализации. Для дефекта найди воспроизведение
   и причину; если причина ещё неизвестна, назови гипотезу и способ проверки.
2. Найди владельца поведения, точки входа, вызывающие стороны, публичные типы,
   существующие тесты и похожее решение. Проследи данные до результата и
   побочных эффектов. Для состояния установи источник истины и жизненный цикл.
3. Проверь команды по `package.json`, конфигурациям тестов и CI именно
   выбранного репозитория. Версии из справочника — снимок, а не основание
   игнорировать текущие файлы. Для вопросов о библиотечном API следуй правилу
   Context7 в `AGENTS.md`; не отправляй секреты в запросы.
4. Для нового механизма или общего контракта прочитай
   [выбор решения](references/implementation-decisions.md) и
   [проверку решения](references/solution-review.md). Для очевидной правки
   достаточно прямого варианта; при неоднозначности сравни только реальные
   альтернативы на одинаковых критериях. Не реализуй несколько вариантов
   ради сравнения.
5. Найди достаточное существующее покрытие и выбери недостающие проверки по
   [качеству тестов](../task-unit-test-coverage/references/test-quality.md).
   Новый тест, браузерный запуск или инфраструктура не нужны по умолчанию.

## Показать короткий план и выполнить

Свяжи требования с конкретными путями, изменением и наблюдаемой проверкой.
Укажи последовательность, зависимости, применимые риски и допущения. Для
малой задачи достаточно нескольких предложений; отдельный файл не обязателен.

Учитывай только затронутые риски: ошибку/пустой ответ, поздний ответ после
смены фильтра, повтор операции, права и изоляцию пользователя, миграцию данных,
совместимость публичного пакета, объём истории или списка. Для runtime-кода
отдельно проверь время свечи, восстановление состояния и согласованность
backtest/replay/signals, если это меняется. Не превращай список в полный аудит.

Для каждой проверки укажи рабочий каталог, существующую команду или ручные
шаги и ожидаемый результат. Планируемый запуск не является выполненным.
Сохраняй [правила ревью](references/review-standards.md).

При разрешённой реализации после плана продолжай без рутинного согласования.
Если пользователь просил только план, остановись перед правками. Блокирующее
решение о потере данных, изменении доступа или внешней операции не подменяй
допущением; продолжай независимую разрешённую часть. Новые технические факты
требуют обновить затронутую часть плана, а не повторять весь процесс.

В конце сопоставь результат с критериями и сообщи фактические проверки и
существенные ограничения. Навык не разрешает публикацию, сообщения, удаление
данных, деплой или изменение внешних систем сверх исходного поручения.
