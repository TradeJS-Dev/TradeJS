# Проверка выбранного решения

Требование, наблюдение и гипотеза механизма — разные вещи. Сохранность данных
может быть требованием; дополнительный запрос или новый store — лишь одним
из решений. Существующий тест внутренних вызовов не делает их обязательными.

Перед реализацией проверь, закрывает ли задачу существующий владелец состояния.
Для простой правки достаточно одного варианта. При неоднозначности сравни
наиболее подходящие варианты, включая прямое изменение текущего потока.
Не создавай формальную матрицу заведомо неподходящих подходов.

Если понадобились дополнительные запросы, подписки, синхронизация состояния
или изменения соседних модулей, вернись к причине: новая сложность нужна
исходной задаче или компенсирует выбранный путь? Обнови план по новым фактам.
Технический пересмотр в разрешённой области не требует нового согласования.

После смены механизма перечитай весь итоговый diff. Проверь оставшиеся
экспорты, настройки, комментарии и тесты отвергнутого подхода; убирай ненужные
собственные добавления в пределах разрешений задачи, сохраняя чужую работу.

Основные ожидания выводи из первичных требований: данные сохранились,
потребитель получил правильный результат, ошибка не показана как успех.
Тест должен допускать другую корректную реализацию. Отдельно проверь ошибки,
отмену и совместимость затронутых входов, если они входят в контракт.
Зелёные внутренние тесты не доказывают необходимость архитектуры.

Глубина проверки соответствует риску. Здесь нет обязательных субагентов,
парных аудитов, специального хранилища планов или нового этапа согласования.
При ответе на ревью сначала перечитай исходный вызов и преобразования именно
обсуждаемой версии; замечание само по себе не расширяет требования задачи.
